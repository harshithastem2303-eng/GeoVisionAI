## 1. Executive status

WASTRAQ today is **two strong, finished halves with no bridge between them**. The property/GIS half is genuinely production-shaped: 16 real surveyed properties on 2nd Cross Road with entrances, frontages and service zones in PostGIS, a complete field-survey and review workflow, a Property Master with audit trail, 11 GIS QA checks, six working web pages, and a spatial association ladder that correctly refuses to guess. The perception half is also real code — RealSense profile negotiation, YOLOv8n + ByteTrack, robust depth sampling, a faithful pure-Python port of librealsense's deprojection — and it is tested to 163 offline assertions. But it has **never produced a single frame from your physical D455**, it emits **camera-local metres only**, and it has **zero lines of code touching the database, a property, a service zone, or a collection event**. Between the two halves sit four components that do not exist in any form: a camera→world coordinate transform, a collection-episode detector, a multi-signal property matcher, and any RFID hardware path. The demo chain you described is currently proven only by `simulation/simulate_picker.py`, which replays a hardcoded coordinate list generated from the same geometry it is testing, and posts to the API over HTTP. **Roughly 15–20% of the intended end-to-end chain exists as running code.**

## 3. What is partially implemented

### 3.1 Confidence scoring — PARTIAL

- **Works:** two real formulas. Containment: `0.95 + min(margin_m/20, 0.04)`. Proximity: `(0.90 − d1/3.0 × 0.15) × (0.6 + 0.4 × separation)`, where `separation = min((d2−d1)/2.0, 1.0)`. Runner-up margin is genuinely computed from the ordered `ST_DWithin` result.
- **Missing:** the containment formula saturates at 0.99 within 0.8 m of the boundary, so on a 4–6 m deep zone essentially every interior point scores 0.99 — it is near-constant in practice. The proximity branch tops out at 0.90 and `simulate_picker.py` requires `>= 0.90` to create an event, so **the entire proximity ladder is unreachable in the shipped demo**. `entrance_distance_m` is computed and returned in every candidate but **never enters the score or any gate**, despite the code comment calling it "a secondary confidence signal".
- **To finish:** decide whether confidence should be a calibrated probability or a display heuristic; if the former, fold in entrance distance, dwell and trajectory agreement, and re-tune against labelled passes.

### 3.2 Collection-event creation — PARTIAL

- **Works:** `POST /collection-events` with lat/lon runs the lookup and 409s on AMBIGUOUS/NO_MATCH. Evidence rows link correctly. `POST /collection-events/{id}/non-segregated` flips status, sets `rfid_triggered`, resolves `rfid_uid → picker`, and creates an evidence row.
- **Missing:** creation with an explicit `property_id` **bypasses the lookup entirely and trusts a client-supplied `association_confidence` verbatim** — and that is the path `simulate_picker.py` actually uses, so the 409 refusal is never exercised by the demo. `event_id` generation is a non-atomic `MAX(...)+1` scan. Four different confidence thresholds are in play (`0.70` in config, `0.85` hardcoded twice in `main.py`/`collection_events.py`, `0.90` in the simulation).
- **To finish:** make the coordinate path the only path for automatic events, or re-verify posted confidence server-side.

### 3.3 Trajectory — PARTIAL

- **Works:** `TrackState.trajectory` is a real 12-second deque of `(t, x, z)` triples with EMA smoothing and a jump gate, bounded to 32 tracks.
- **Missing:** it is **in-process RAM only**. No table, no file, no persistence, and it is dropped on restart. `y` is discarded from the trail.
- **To finish:** a `picker_tracks` / `track_points` table, or at minimum a ring buffer that survives long enough to be queried by an episode detector.

### 3.4 Geometry versioning — PARTIAL

- **Works:** `property_geometry_history` is written by a real `BEFORE UPDATE OR DELETE` trigger on all three geometry tables, so QGIS edits are versioned too. Proven live in `verify_demo.sh` §11 by an UPDATE inside a rolled-back transaction.
- **Missing:** no INSERT trigger, so the first version of a feature is never snapshotted. `changed_by` records `OLD.created_by`, which `_upsert_geometry` overwrites with the *current* editor — so history attributes each change to the **previous** editor. `version` is incremented only by the API, so a QGIS edit produces a history row with an unchanged version number.

### 3.5 Reviewer UI — PARTIAL

- **Works:** approve and return-for-correction, with role enforcement (403 for a surveyor attempting approval).
- **Missing:** `REJECT` is a valid server outcome with **no button anywhere in the UI**. "Notes required when returning" is enforced only in the browser; `review_notes` is optional server-side.

### 3.6 Evidence — PARTIAL (records only)

- **Works:** rows insert, link to events, and query back correctly.
- **Missing:** `file_path` comes from `models.fake_evidence_path()`. **No file is ever written, none is ever served, and existence is never checked.** The dashboard's evidence modal displays the *survey frontage reference photo* under a heading immediately above the placeholder table — easy to misread as evidence media during a demo. (The modal does carry an honest disclaimer.)

## 6. RFID status

**Verdict: MOCK. This is the least-built subsystem in the project.**

- **Hardware assumptions:** ESP32 + MFRC522 per your brief. **Nothing in the repo reflects this.** Repo-wide grep for `esp32|mfrc|rc522|arduino|platformio|\.ino` returns **zero matches**.
- **ESP32/MFRC522 code:** **DOES NOT EXIST.** No firmware, no sketch, no serial/MQTT/HTTP client, no `secrets.h`.
- **Backend endpoints:** exactly **one** touches RFID — `POST /collection-events/{event_id}/non-segregated` (`routes/collection_events.py:171`). It is **not device-facing**: no auth, no device ID, no ingest schema, and it requires the caller to already know an `event_id`. **There is no `POST /rfid/tap` or equivalent — a reader has nowhere to send a tap.**
- **Database storage:** two columns and no table. `pickers.rfid_uid TEXT UNIQUE` (`schema.sql:117`), `collection_events.rfid_triggered BOOLEAN` (`schema.sql:141`). **`rfid_events` / `rfid_taps` do not exist.** Taps are not persisted; only a boolean on the event survives.
- **Worker identity mapping:** the entire logic is four lines — `SELECT * FROM pickers WHERE rfid_uid = %s`, 404 if unknown, then overwrite the event's `picker_id`. Seed UIDs are `RFID-DUMMY-A1B2C3D4` / `RFID-DUMMY-E5F6A7B8`.
- **Timestamping:** **none.** The request carries no tap timestamp. `collection_time` is untouched; evidence `captured_at` is `datetime.now(timezone.utc)` at server-receive time. No device clock, no skew handling, no ordering.
- **Deduplication:** **none.** Posting the same tap N times flips the same event N times and creates N evidence rows.
- **Offline queue:** **none**, for RFID or anything else.
- **Only caller in the repo:** `simulate_picker.py:216`, hardcoding `RFID-DUMMY-A1B2C3D4` against `created[-1]`.

**What is missing before RFID can participate in the final demo:**
1. ESP32 firmware (MFRC522 read → Wi-Fi → HTTP POST) with `secrets.h` + `secrets.example.h`.
2. A device-facing `POST /rfid/tap {reader_id, rfid_uid, tapped_at, seq}` with a shared-secret header.
3. An `rfid_events` table storing every tap with device time, server time and reader ID.
4. Idempotency on `(reader_id, seq)` or `(rfid_uid, tapped_at)` — an ESP32 retrying over flaky Wi-Fi will double-post.
5. A correlation query: tap → picker → **most recent eligible collection episode within N seconds**. This does not exist even in outline, because episodes do not exist (§4).
6. A local queue on the ESP32 for taps recorded while Wi-Fi is down.
7. A UI button, so the exception path is demonstrable without curl.

## 7. RealSense / vision status — the critical section

**Does RealSense support exist in the repo?** **Yes, as real code. No, as a working capture path.**

- **Real SDK integration:** `RealSenseSource` (`vision/pipeline.py:153-376`) uses `rs.context()`, `rs.config()`, `rs.pipeline()`, `cfg.can_resolve(rs.pipeline_wrapper(...))`, `rs.align(rs.stream.color)`, `wait_for_frames(timeout_ms)`, `first_depth_sensor().get_depth_scale()`. `import pyrealsense2 as rs` happens **inside `open()`**, never at module import — verified by a test asserting `"pyrealsense2" not in sys.modules` after importing the package.
- **Model assumptions:** **none hardcoded.** No `D455`/`product_line` check anywhere; `open()` takes `devices[0]`. D455 appears only in a comment, a test fixture name and the README. Instead of assuming a model, `enumerate_stream_profiles()` + `select_stream_profile()` negotiate: exact resolution → same aspect ratio → closest pixel count → exact fps → **a rate at or below the request, never faster** → format preference (`bgr8` first). This is pure Python and tested with a synthetic D455-shaped catalogue.
- **SDK/dependency status:** `pyrealsense2.cpython-311-darwin.so` **is present** in `.venv/lib/python3.11/site-packages/` — hand-built, since PyPI publishes no Apple-Silicon wheel (`requirements-vision.txt` markers exclude Darwin/arm64 deliberately). `ultralytics 8.4.126`, `opencv-python 4.14`, `torch` and `numpy` are all installed. `models/yolov8n.pt` is present (6.3 MB).
- **How frames/depth are accessed:** one background thread owns the camera; HTTP handlers only read snapshots under a lock. Depth is **aligned into colour** before use, and intrinsics are taken from the **colour** stream accordingly. Two separate timeouts: `VISION_STARTUP_TIMEOUT_MS=10000` for the first frameset, `VISION_FRAME_TIMEOUT_MS=2000` for steady state, plus 10 discarded warm-up framesets.
- **Does person detection work?** The code is complete and correct-looking. **It has never been run on a real camera frame.** It is proven only against synthetic RGB-D in `test_vision_logic.py` §10.
- **Detector:** Ultralytics YOLOv8n, `classes=[0]` (person), `conf=0.35`, `imgsz=640`, device auto-selected (MPS on your Mac).
- **Multi-person tracking:** yes — ByteTrack via `model.track(persist=True, tracker="bytetrack.yaml")`. Real persistent IDs. Detections with no tracker ID are dropped. **No re-identification**: ByteTrack's `track_buffer` is never configured, so a multi-second occlusion yields a new ID — `docs/VISION.md:316` promises re-association that the code does not implement.
- **Is depth associated with tracked people?** Yes, and carefully. Ground-contact anchor (bottom-centre lifted 6% of box height), falling back once to a torso anchor at 40% and **reporting which anchor was used**. 9×9 window; drop zeros and out-of-range (0.3–10.0 m); require ≥6 valid; take the 25th percentile and keep values within 0.30 m of it; median. Below threshold → `depth_valid: false` and a **null** position. **No coordinate is ever invented.**
- **Are 3D/local coordinates produced?** Yes — **camera-local metres only**. `deproject()` is a branch-for-branch pure-Python port of `rs2_deproject_pixel_to_point`, supporting `none`, `inverse_brown_conrady` (forward polynomial, matching real D400 behaviour), `brown_conrady` (10-iteration inverse) and `kannala_brandt4` (4-iteration Newton), and **refusing** `modified_brown_conrady` outright. Cross-checked against an independent transcription to `< 1e-12`.
- **Is any trajectory generated?** Yes — 12 s of `(t, x, z)` per track, EMA-smoothed with a jump gate, in RAM, never persisted.

### The blocking fact

`logs/backend.log` ends with repeated `RealSense not available (no RealSense device found on USB); retrying in 15s` — the SDK imports fine, the camera simply wasn't attached. And **there is no hardware-test log anywhere in `logs/`**. The last recorded hardware attempt (documented in your phase-3b build log) was: SDK imports, D455 connects, both streams report OK, intrinsics read, YOLO loads, ByteTrack active — **then `Frame didn't arrive within 2000` forever, with 0 frames processed**, while `sudo rs-capture` showed live depth on the same machine. Three defects were then fixed (guessed-not-negotiated profile, one timeout doing two jobs, no warm-up) and USB-2.1 downgrade detection was instrumented. **That fix has never been run against the physical camera.** It is an untested hypothesis.

**What has to be built next, in order:**
1. Run `scripts/test_realsense_picker_tracking.py` with the D455 attached and confirm stages 1–6 pass. Until this happens, every perception percentage in §13 is a projection.
2. A **ground-plane calibration**: fit the floor from depth, so `y` becomes height above ground rather than a raw optical-frame value.
3. A **camera→lane transform**: two or more surveyed reference points visible in frame, solved for a rigid 2-D transform from camera-local X/Z to EPSG:32643, then to 4326. This is the single missing link between the two halves of the project.
4. Trajectory persistence.
5. A dwell/episode detector over the persisted trajectory.
6. Frame retention so an episode can yield an evidence clip.

**Fix worth making today (5 minutes):** `pipeline.status()` returns `device`, `usb_type`, `negotiated_color_profile`, `negotiated_depth_profile` and `first_frame_ms`, but **none of these are declared on the `VisionStatus` pydantic model**, so FastAPI strips all five from the HTTP response. `picker-tracking.html:225` renders `s.device`, which will therefore **always show `—`** even with a camera streaming. The offline tests miss it because they call the route function directly, before response-model filtering.

## 15. Recommended next implementation sequence

Constraints assumed: Intel RealSense D455, MacBook, no external IMU, no RTK, existing 16-property lane, ESP32+MFRC522 available. Shortest path to a *convincing* demo, not a complete system.

### Milestone 0 — Prove the camera (blocks everything; 1 day)
Attach the D455 and run `.venv/bin/python scripts/test_realsense_picker_tracking.py --view`, stage by stage. If stage 1 reports USB 2.1, change the cable/port first — no software fix helps. Do not proceed until stage 6 prints live X/Z for a walking person. **If this fails, everything below is unschedulable.** While you are in there, add the five missing fields to `VisionStatus` so the page stops showing `—`.

### Milestone 1 — Camera to lane coordinates (2–3 days)
The one piece that connects the project's halves.
- Fit a ground plane from depth over a few seconds of empty floor; express positions as height-above-ground + a 2-D ground position.
- Place the camera at a **surveyed fixed origin** on the lane with a known heading. Sight two surveyed markers (two entrance points work) and solve a rigid 2-D transform camera-local → EPSG:32643 → EPSG:4326.
- Extend `/vision/tracks` with an optional `world` block: `{lat, lon, accuracy_m, transform_id}`, **null when uncalibrated** — the same discipline the depth code already uses.
- Test it the way this project tests things: stand on a surveyed entrance, assert the reported lat/lon lands inside that property's service zone.

**Do not add GNSS.** A surveyed fixed origin is more accurate than any consumer receiver and makes the demo repeatable.

### Milestone 2 — Persist tracks (1 day)
`picker_tracks` (track_id, session_id, started_at, ended_at) and `track_points` (track_id, t, x_m, z_m, lat, lon, depth_valid). Write from the camera thread on a small batched queue. This is what makes episodes, evidence and dispute review possible.

### Milestone 3 — Collection episode detector (2–3 days)
A small state machine over persisted track points: `APPROACHING → DWELLING → DEPARTED`. Dwell = speed below a threshold for ≥ N seconds within M metres of a service zone. Emit a `collection_episodes` row with start, end, centroid, and the candidate property set from `lookup_property`. Debounce so one pass yields one episode per property.

### Milestone 4 — Multi-signal matcher (2 days)
Score each candidate over the **whole episode**, not one point: fraction of dwell samples inside each zone; mean distance to entrance; direction of approach relative to the frontage; whether the trajectory crossed the frontage line (this is what `property_frontages` is *for*, and it is currently unused). Keep the refusal semantics — `AMBIGUOUS` stays a first-class outcome. Move all thresholds into `config.py` and delete the three hardcoded duplicates.

### Milestone 5 — Evidence capture (1–2 days)
Keep a rolling in-memory buffer of annotated JPEGs. On episode close, write 3–5 stills (and optionally a short clip) under `EVIDENCE_DIR`, insert real `evidence` rows, and add a `GET /evidence/{id}/file` with the same path-jail pattern already correct in `survey/actions.py:580`. Delete `fake_evidence_path()`.

### Milestone 6 — RFID for real (2–3 days)
- ESP32 + MFRC522 sketch: read UID → HTTP POST → LED/buzzer feedback → local queue if Wi-Fi is down. Ship `secrets.example.h`; keep `secrets.h` gitignored (the `.gitignore` already handles this).
- `POST /rfid/tap {reader_id, rfid_uid, tapped_at, seq}` with a shared-secret header, writing to a new `rfid_events` table.
- Correlation: tap → picker → **most recent open or recently-closed episode for that picker within N seconds** → flip that episode's event to `NOT_SEGREGATED` and attach evidence. Idempotent on `(reader_id, seq)`.

### Milestone 7 — Make it visible (1–2 days)
Add the live picker position to the operations dashboard map (it already renders zones and entrances). Add an episode feed alongside the event feed. Add a manual non-segregation button so the exception path is demonstrable without an ESP32 on stage.

### Milestone 8 — Re-verify (half a day)
Re-run `verify_demo.sh` against 0.5.0+, add assertions for the new tables, and fix the two invariants that fail on legitimate use (re-survey, 17th property).

**Total: roughly 12–17 working days**, with Milestone 0 as a hard gate. If the camera cannot be made to deliver frames, stop and solve that alone — nothing else is worth starting.
